# Project Compass

> 保存项目相对稳定的方向性判断。它是当前最优参考，不是不可质疑的命令。

最后复查：2026-07-22

## 项目目的

完成一款可在手机竖屏环境运行的《掌眼》游戏本体，让玩家在古玩鉴定与交易博弈中通过证据、陈述变化和交易条件管理不确定性。

## 目标用户或受众

- 当前直接验收者：指导老师；验收对象是可运行的游戏本体。
- 最终玩家画像尚未确认，不把“老师验收”误写成长期目标用户定义。

## 核心价值或体验

玩家不是猜表情或做真假二选一，而是在有限行动点和信息不对称中，把不可验证的故事逐步转化为可核验的证据和有成本的承诺。

## 成功标准

- 能独立走完观察 → 证据整理 → 行动 → NPC 回应 → 交易处置 → 复盘的核心闭环；
- 玩家能说清证据簿与行动入口的职责区别；
- NPC 状态变化可追踪、可解释、可复现；
- 按“玩法完整度 → 视觉效果 → 技术实现 → 文化内容”的顺序逐层提高完成度。

## 不可牺牲原则

- 物品真相、NPC 认知、NPC 陈述和 NPC 状态分层；
- 证据优先于情绪读取，结算不能退化为真假二选一；
- UI 不直接决定 NPC 结果，正式结果必须来自可测试的规则链路；
- 技术路线未验证前，不因单一经验或传闻作不可逆选择。

## 硬约束

- 2D、手机竖屏、最终载体为 H5；
- 计划周期约 7 周、210 小时；
- 项目组负责游戏从设计到开发，老师负责建议和指导；
- 当前仍是低保真交互与规则可解释性验证阶段。

## 明确非目标

- 当前阶段不平衡正式价格、底价、折价和检测成本；
- 当前阶段不接生产 API、不做正式登录、云存档或大量正式内容；
- 当前阶段不以视觉精修替代玩法闭环验证。

## 重新讨论触发条件

- 新证据直接否定核心价值或受众假设；
- 约束、成本或项目范围发生实质变化；
- 已批准的成功标准无法被可行方式验证。
- 最终分发入口明确要求“微信小游戏”而不是浏览器 H5，或明确要求某个引擎工程；
- 技术样片证明当前 Web 路线无法满足性能、包体、发布或关键交互要求。
