# Next Actions

> 推荐能够以较低成本减少最大重要未知、风险或阻塞的行动，而不是机械维护功能清单。

更新时间：2026-07-22

## 推荐主路径

先实现最小可测试规则切片：把一次“专业 + 指出矛盾 + 现代胶痕”行动转换为四项 NPC 状态 delta 和原因日志，再让 UI 渲染该结果。

## 为什么现在做

当前最大玩法未知不是画面，而是精确数值能否以可解释、可复现的方式支持 NPC 改口。该切片能最早暴露规则是否合理，同时避免提前处理价格和大规模内容。

## 要减少的核心未知或风险

- 精确数值目前只是人为写入 UI，无法验证规则链路；
- UI 与规则系统的边界尚未被真实代码证明；
- 玩家是否能从四项变化理解“为什么 NPC 改口”尚未验证。

## 完成标准

- 输入固定 `initialState + PlayerAction + seed` 时输出固定四项状态和 eventLog；
- UI 不再硬编码 P5 的 after 数值，只读取规则输出；
- 自动测试覆盖同输入同结果、阈值触发和数值边界；
- 单文件演示继续可用，并能清楚标记正式计算与残余 Mock。

## 前置条件

- 暂时接受当前四项数值作为工作样例，不把它们视为最终平衡；
- 不需要先决定正式价格或完成视觉资产；
- 最终技术路线只需保持未锁定，不阻塞规则接口设计。

## 结果分支

- 如果规则切片能稳定解释 NPC 改口：扩展到温和/强硬分支并做一次小规模试玩；
- 如果数值难以解释或需要 UI 特判：先修正规则变量、阈值和事件日志，再扩页面。

## 暂时不做

- 正式价格与交易平衡；
- 大量器物内容、生产 API、登录与云存档；
- 在分发入口未澄清前迁移到 Unity。

## 备选行动

低成本备选：先向同事确认其所说的“微信 H5 小游戏”究竟指微信内网页还是微信小游戏，并记录目标入口、包体限制和提交方式；该信息用于安排后续技术样片，但不阻塞规则切片。
