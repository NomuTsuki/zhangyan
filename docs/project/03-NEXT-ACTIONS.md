# Next Actions

> 推荐能够以较低成本减少最大重要未知、风险或阻塞的行动，而不是机械维护功能清单。

更新时间：2026-07-23

## 推荐主路径

先让用户审阅已经可运行的独立定价数值实验台，集中确认三个参数边界：两倍级 NPC 错价应多罕见、默认采用哪个风险分位、NPC 开价是否作为可见似然进入玩家价值后验。确认后调参并复跑 10,000—50,000 局；只有黄色警报和统计口径得到认可，才把一类器物与三类 NPC 接入教师演示 HTML。暂不增加第二案件或精修美术。

## 为什么现在做

首轮实验已证明五档混合、市场两端扰动、Qα 与有限议价在技术上可运行，但也发现普通藏家两倍级错价达到 `34.8%`，市场事件下约 `42.6%`，不符合“巨大错价低频”的设计方向。此时直接接入正式循环会把错误参数固化进玩法；先用现成实验台确认目标并复跑，成本最低、学习价值最高。

## 要减少的核心未知或风险

- 玩家是否能区分“客观赚亏”和“当时依据是否合理”；
- 单一后验中位数是否足够谨慎，还是应以更低分位数作为“保守收购上限”；
- “巨大错价低频”具体是低于 `5%`、`10%`、`15%` 还是其他范围，以及是否按 NPC 类型分别设定；
- NPC 开价是否只作为交易侧信号展示，还是应以有噪声似然更新玩家价值后验；
- 市场日报提高两端概率后，玩家能否从多案证据中学习，而不是把结果理解成纯抽奖；
- NPC 有限耐心能否支持多轮议价，同时避免免费反推底价；
- 6 点共享预算会不会过紧、过松，或让某条路线天然支配其他路线；
- 送检 `2 AP + 10价值点` 是否真有代价但又不是永远不值得；
- 重复询问、无依据质疑、证据支持追问的反馈是否足够可理解；
- 观察线索是否温和导向下一步，而不是明示答案或完全依赖运气；
- 局末完整公式对项目沟通是否有帮助，哪些内容应保留为开发调试而非玩家复盘。

## 建议试玩记录

每局至少记录：

1. 每回合选择、理由、剩余行动点；
2. 玩家当时认为的真相概率和可接受价格；
3. 是否打开证据簿、是否使用陈述证据、是否考虑送检；
4. 最终购买、折价或拒绝的理由；
5. 看完复盘后能否用自己的话解释客观分与判断分；
6. 哪一次反馈最意外、哪一个按钮或数值最困惑。

## 完成标准

- 用户确认错价目标频率、默认风险分位与 NPC 开价的信息角色；
- 调参后的 10,000 局基准不再把“巨大错价”误作常态，并保留外行、藏家、商贩之间清楚差异；
- Qα 全样本覆盖、成交后亏损和正上限利润缓冲继续使用三个独立口径；
- 玩家与 NPC 轨迹继续分账，接受、还价、拒绝、离场可达且所有 AP 边界零死锁；
- 通过后将一类器物和三类 NPC 接入教师演示 HTML；
- 至少完成一次教师演示和 3—5 局独立试玩；
- 没有玩家因行动点耗尽、NPC 离场或证据簿导航而无法结束；
- 能列出至少两条真实采用的证据路径，而不是所有人机械复制同一路线；
- 能判断送检、折价或某种态度是否形成支配策略；
- 根据记录形成一组明确调参建议：行动预算、成本、NPC 权重、线索文案或复盘呈现；
- 规则变更后继续保持主规则与独立 HTML 差分一致。

## 前置条件

- 先只使用游戏内虚拟价值和离散参数，不接真实市场价格；
- 将器物价值后验与 NPC 接受线后验分开，任何推荐系统不得读取隐藏真相；
- 直接使用当前自包含 HTML，无需先部署、迁移 Unity 或接入真实市场数据库；
- 教师演示默认真相可以固定，以便讨论规则；平衡验证再用三个真相变体回放；
- 试玩前不向玩家展示隐藏真相、底价和接受线。

## 结果分支

- 如果两倍级错价仍过高：优先降低 NPC 私有信号噪声和锚定波动，不压缩器物本身的珍品长尾；
- 如果精明 NPC 使Q线成交样本出现高逆向选择：把 NPC 档案与开价历史作为玩家可见似然，或明确把Q线命名为“器物证据下限”而非安全报价；
- 如果Q20长期上限为0或成交过低：先比较Q25、费用和利润缓冲，不直接改用会被长尾抬升的均值；
- 如果阶梯议价形成固定脚本：提高状态依赖、证据方向性或人物让步差异，而不是增加无限轮数；
- 如果双层胜负难懂：先调整结算文案和信息层级，不立即改评分公式；
- 如果唯一正确路线过强：增加可替代证据链或调整观察导向；
- 如果送检支配其他策略：提高机会成本、增加 NPC 同意条件或缩小检测范围；
- 如果送检无人使用：降低成本或让它解决更明确但有限的未知；
- 如果 6 AP 经常导致无意义的被迫结束：提高预算或减少低价值重复成本；
- 如果玩法闭环被理解且选择分布健康：再进入第二案件与内容验证。

## 暂时不做

- 真实市场价格、正式经济系统与大量器物估值；
- 每日在线刷新、可反复重抽的市场事件或会被 jackpot 击穿的长期货币循环；
- 第二案件、大量美术、登录、云存档或生产后端；
- 在分发入口未澄清前迁移 Unity；
- 把开发侧栏中的全部公式直接搬进手机玩家 UI。

## 后续技术动作

试玩结论稳定后，再做一个小型技术路线比较：标准 Web/H5 与 Unity/微信小游戏分别验证启动速度、包体、手机适配、团队学习成本和发布流程。独立 HTML 与 TypeScript 目前是两份规则实现，正式开发前应统一规则源，或把差分测试固化为持续检查。
