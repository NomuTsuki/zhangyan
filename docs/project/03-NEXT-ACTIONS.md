# Next Actions

> 推荐能够以较低成本减少最大重要未知、风险或阻塞的行动，而不是机械维护功能清单。

更新时间：2026-07-23

## 推荐主路径

先用当前单文件 HTML 做一轮结构化试玩，而不是立即增加第二案件或精修美术。让老师和少量体验者各自完成一局，并记录他们在每个行动点上的选择理由、对线索的理解、对交易风险的判断，以及局末是否能解释双层结果。

## 为什么现在做

多轮规则、无死局终局、NPC 纺锤决策与局末公式已经实现并通过自动验证。继续只在代码中调参，无法回答目前最重要的三个问题：玩家是否理解线索导向、6 点预算是否形成有效取舍、双层胜负是否清楚。一次受控试玩比扩功能更能降低不确定性。

## 要减少的核心未知或风险

- 玩家是否能区分“客观赚亏”和“当时依据是否合理”；
- 6 点共享预算会不会过紧、过松，或让某条路线天然支配其他路线；
- 送检 `2 AP + 10价值点` 是否真有代价但又不是永远不值得；
- 重复询问、无依据质疑、证据支持追问的反馈是否足够可理解；
- 观察线索是否温和导向下一步，而不是明示答案或完全依赖运气；
- 局末完整公式对项目沟通是否有帮助，哪些内容应保留为开发调试而非玩家复盘。

## 建议试玩记录

每局至少记录：

1. 每回合选择、理由、剩余行动点；
2. 玩家当时认为的真相概率和可接受价格；
3. 是否打开证据簿、是否使用陈述证据、是否考虑送检；
4. 最终购买、折价或拒绝的理由；
5. 看完复盘后能否用自己的话解释客观分与判断分；
6. 哪一次反馈最意外、哪一个按钮或数值最困惑。

## 完成标准

- 至少完成一次教师演示和 3—5 局独立试玩；
- 没有玩家因行动点耗尽、NPC 离场或证据簿导航而无法结束；
- 能列出至少两条真实采用的证据路径，而不是所有人机械复制同一路线；
- 能判断送检、折价或某种态度是否形成支配策略；
- 根据记录形成一组明确调参建议：行动预算、成本、NPC 权重、线索文案或复盘呈现；
- 规则变更后继续保持主规则与独立 HTML 差分一致。

## 前置条件

- 直接使用当前自包含 HTML，无需先部署、迁移 Unity 或接入真实市场数据库；
- 教师演示默认真相可以固定，以便讨论规则；平衡验证再用三个真相变体回放；
- 试玩前不向玩家展示隐藏真相、底价和接受线。

## 结果分支

- 如果双层胜负难懂：先调整结算文案和信息层级，不立即改评分公式；
- 如果唯一正确路线过强：增加可替代证据链或调整观察导向；
- 如果送检支配其他策略：提高机会成本、增加 NPC 同意条件或缩小检测范围；
- 如果送检无人使用：降低成本或让它解决更明确但有限的未知；
- 如果 6 AP 经常导致无意义的被迫结束：提高预算或减少低价值重复成本；
- 如果玩法闭环被理解且选择分布健康：再进入第二案件与内容验证。

## 暂时不做

- 真实市场价格、正式经济系统与大量器物估值；
- 第二案件、大量美术、登录、云存档或生产后端；
- 在分发入口未澄清前迁移 Unity；
- 把开发侧栏中的全部公式直接搬进手机玩家 UI。

## 后续技术动作

试玩结论稳定后，再做一个小型技术路线比较：标准 Web/H5 与 Unity/微信小游戏分别验证启动速度、包体、手机适配、团队学习成本和发布流程。独立 HTML 与 TypeScript 目前是两份规则实现，正式开发前应统一规则源，或把差分测试固化为持续检查。
