# Next Actions

> 推荐能够以较低成本减少最大重要未知、风险或阻塞的行动，而不是机械维护功能清单。

更新时间：2026-08-03

## 推荐主路径

先完成 V1 教师交付，再从明确冻结点启动 V2。

V1 正式提交主体是最新评分修正版。只沿已批准的方案二推进：

1. 在 codex/v1-teacher-finalize 工作树审定“最小交付修正”清单；
2. 只修复会破坏教师交付一致性、仓库可理解性或基础验证可信度的问题；
3. 编写一份能让老师结合演示完整理解项目的项目说明；
4. 编写简洁的演示操作说明，并明确开发栏不是玩家 UI；
5. 重新运行自动化、构建和关键真实浏览器路径；
6. 形成一个明确的 V1 冻结提交与冻结引用；
7. 从冻结点制作教师提交包，核对包内文件与说明中的哈希或版本。

当前预检只完成了安全保全、坏引用隔离、定稿工作树和决策记录。上面的代码修正、说明、冻结与打包尚未执行。

## 完成标准

V1 教师交付阶段只有同时满足下列条件才算完成：

- 最小修正的范围和理由可逐项说明；
- 自动化、类型、Lint 与关键浏览器路径有新鲜证据，已知失败被修复或以批准的门禁边界明确处置；
- 项目说明与演示说明能够和 canonical 高保真文件相互对应；
- 教师提交包只包含审定文件，且可追溯到一个明确冻结提交；
- 冻结引用已经创建并验证，原工作区未提交内容仍可恢复；
- 项目记忆准确区分 V1 已实现内容、尚未验证内容和 V2 规划。

## V1 最小修正准入门

一个问题只有同时满足以下条件，才进入 V1：

- 能在当前教师交付路径或仓库说明中复现；
- 不改变已批准的核心玩法、评分方向、信息边界或视觉方向；
- 修改范围有限，有对应的回归或人工验收；
- 不要求统一所有数值实现、增加第二案件或搭建正式运营系统。

当前已知候选是完整测试中的低保真 standalone-html 静态断言与现行实现不一致。是否修改测试、恢复缺失实现或明确移出交付门禁，必须先做语义审查，不能仅为了“全绿”机械改字符串。

## 教师理解与真人验证边界

用户已经确认：老师能够找到关键按钮、理解证据公开并完成交易，因此这项不再阻塞 V1。

仍未被这项确认覆盖的是：

- 一般目标玩家能否无讲解理解；
- 不同案件和不同难度是否仍然成立；
- 没有显式 anchor 标签时，信息披露是否自洽；
- 随机种子和工作参数变化后，判断质量与结算是否公平；
- 微信内置浏览器、Safari、极窄屏、软键盘和真实设备 safe-area。

这些内容应作为 V2 的分层验证，不用一个过于简单的演示案替代。

## V2 启动触发器

只有 V1 已形成明确冻结点后，才启动 V2。不要手工复制出一个失去历史关系的普通文件夹；优先从冻结提交建立新的 Git 分支与独立工作树。

V2 的启动顺序：

1. Agent 先只读审查 V1 冻结点、Git 状态、保留内容、数值定义位置、实验台、单文件、测试、文档和 Agent 框架；
2. 审查后主动告诉用户：统一数值权威源已经获批，是 V2 第一项核心产品工程；
3. 报告冲突、迁移边界、保留资产、回滚方式和验证门槛；
4. 在没有新重大冲突时，为数值权威源统一编写并执行独立计划；
5. 再在统一内核之上逐步发展多案件、自动化和可调的低认知门槛层。

仓库审查与 Agent 框架检查是启动前置，不取代第一项产品核心工程。

## V2 第一项核心工程的完成定义

- 每个数值模块有一个明确的生产权威源；
- 高保真、低保真、数值实验台、单文件和测试不再各自复制核心公式；
- 实验参数、生产参数、显示投影和调试数据有明确边界；
- 单文件由构建生成并能追溯到源提交；
- 现有回归测试按“代码一致性、设计例证、批量平衡、真人体验”分层，不再用测试通过代替玩法正确；
- 迁移可以分批回滚，并保持 V1 冻结版不变。

## 暂时不做

- 不把根工作区的 31 个混合文件整包复制进 V1；
- 不在 V1 统一全部数值系统；
- 不在 V1 增加第二案件、低中高级场或长期经济；
- 不迁移 Unity，不制作微信小游戏工程；
- 不把老师理解当前演示等同于目标玩家验证；
- 不在 V1 封存前更换项目 Agent 架构；
- 不推送、部署或公开托管，除非用户另行授权。
