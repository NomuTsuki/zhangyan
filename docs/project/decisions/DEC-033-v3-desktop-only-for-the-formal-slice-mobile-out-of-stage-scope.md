# DEC-033：V3 正式切片只做桌面尺寸，手机端明确移出本阶段范围

Status: Active

日期：2026-08-28

## 为什么现在决定

`AGENTS.md` 的视口政策带一条强制提醒：**一旦开始制作高保真原型或正式页面，必须主动提醒用户重新决定移动端约束，不得默认沿用桌面尺寸。** 2026-08-28 用户宣布接下来两周的目标是"把这个完整正式的切片开发出来"，"正式"触发该提醒，提醒已发出并已由用户答复。

不等到做完再问，是因为 [DEC-032](DEC-032-v3-workbench-map-separation-and-guidance-division.md) 的结构对视口敏感到无法后补：它要求**行动面在左、认知面在右**。竖屏没有"左右"，硬移植只能改成上下切换或标签页——那是另一套信息架构，不是同一套布局的响应式变体。等呈现变体做完再改等于重做。

## 当前决定

**本阶段（V3 正式切片）只做电脑浏览器尺寸。手机端不在范围内，且不为其预留布局退路。**

这把 2026-08-24 的**临时豁免**（原措辞是"**先**按电脑浏览器尺寸制作，**暂**不受手机竖屏约束"）转为本阶段的**明确范围决定**。差别在于：豁免意味着迟早要回来，范围决定意味着这一阶段不回来，而且允许做出竖屏无法承载的设计。

具体含义：

- DEC-032 的左右分区可以放心建，**不必留竖屏退路**；
- 不做响应式断点，不做上下折叠变体，不做窄屏降级；
- 作品集资产继续按桌面尺寸采集（与 594×210mm 横向跨页方向一致，见 `portfolio-capture`）；
- 真人测试在电脑上进行，测试结论的适用范围也仅限桌面。

## 这个决定不做的事

- **不改变产品定性。** 项目在《工作总结报告》里的自我描述是"《掌眼》微信端 H5 小游戏"，微信端天然偏手机。本决定**不撤销**这一定性，只声明当前阶段不实现它。
- **不撤销 [DEC-008](DEC-008-standard-web-h5-delivery.md)。** H5 不等于手机：桌面浏览器页面同样是 H5，两者不冲突。
- **不改动 V1/V2。** 两者的 390×844 手机竖屏是既成历史事实，其归档资产按 `portfolio-capture` 继续保持手机竖屏，不重新采集。
- **不承诺未来做手机端**，也不否认。该问题留待产品定性再次被讨论时处理。

## 必须记在账上的欠款

**如果产品定性最终仍是微信端小游戏，那么欠一次完整的竖屏信息架构设计。** 它不是"把桌面版缩小"，至少要重新回答：

- 行动面与认知面在没有左右的屏幕上如何共存（上下分屏？标签切换？抽屉？）；
- DEC-032 的两拍反馈动画在小屏上还看不看得清飞线与整图重组；
- 决策面四类在竖屏上是否还能同屏可比——不能同屏比较的话，"多个缺口并列且不排序"这条反派工判定标准就失效了。

**第三条是真正的风险：它不是适配问题，是这个决定可能与 DEC-032 的核心保证冲突。** 现在不解，但必须记着。

## 与本阶段目标的关系

本决定为期两周的线上阶段服务：目标是把正式切片做出来，而非做完整产品。用户已明确作品集申请截止在 2026-10-20 之前，因此作品集拼版不占用这两周，但采集照旧按里程碑进行。

## 重新讨论触发条件

- 产品定性被重新讨论，尤其是"是否仍为微信端小游戏"；
- 出现真实的手机端交付要求（导师、投放、演示场合）；
- 桌面版真人测试通过后进入实际上线准备；
- 作品集或答辩需要手机形态的画面；
- DEC-032 的结构在桌面上被证伪，需要重新选型（此时视口约束也应一并重选，不要单独继承）。

## 当前信心

**高：** 现在决定比事后决定省事；左右分区与竖屏确实不兼容；本阶段两周内做不完两套信息架构。

**中：** 桌面独占是否会让"微信端小游戏"这一定性显得名不副实——取决于最终如何叙述这个项目。

**低 / Unknown：** 竖屏上"多个缺口并列且不排序"能否成立。未做任何验证，纯属已识别但未解决的风险。
