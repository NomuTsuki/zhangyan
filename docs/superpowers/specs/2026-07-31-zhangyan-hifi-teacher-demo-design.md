# 《掌眼》高保真教师演示设计规格

日期：2026-07-31
状态：已确认（2026-07-31）
目标文件：`prototype/public/掌眼_高保真教师演示.html`

## 1. 目标

在不覆盖现有低保真原型和数值实验台的前提下，新增一份可离线双击打开、可完整走通首案、接近真实 H5 游戏观感的高保真教师演示。

这份演示必须同时证明：

- 《掌眼》的调查、取证、询问、议价和结算能够形成清楚的玩家任务流；
- 玩家界面与开发调试信息严格分层；
- 新批准的等级制、双资源和具体证据披露已经进入交互；
- 视觉精修没有绕过规则链路或伪造结果。

## 2. 明确不做

- 不覆盖 `掌眼_低保真交互原型.html`；
- 不修改 `掌眼_数值实验台.html` 的开发工具定位；
- 不制作第二案件、长期经济、登录、存档、联网服务或 Unity 工程；
- 不接真实古董市场价格；
- 不把本轮视觉完成描述成数值平衡、文化内容或正式美术资产已经验收；
- 不为当前低价值首案制作结算后的写实器物讲解图；该内容留给后续精品、珍品案件；
- 不在玩家主界面公开隐藏真相、NPC 底线、后验概率、候选评分或公式。

## 3. 选定视觉方向

采用“当代雅集式鉴定工作台”。

### 3.1 气质

- 专业、克制、安静；
- 有中国古玩与漆器辨识度，但不做仿古网页；
- 让器物、证据和人物陈述成为视觉主角；
- 使用现代信息层级和触控反馈，不依赖装饰性书法表达重要信息。

### 3.2 色彩

| 角色 | 色值 | 用途 |
|---|---|---|
| 墨松 | `#173F38` | 主导航、主要按钮、关键状态 |
| 暖纸 | `#F5EFE3` | 玩家画布底色 |
| 宣纸白 | `#FFFDF7` | 卡片、浮层、输入区 |
| 漆朱 | `#9B3F32` | 风险、价格变化、关键证据 |
| 铜金 | `#B28A4C` | 品质、等级、稀有线索 |
| 墨黑 | `#1D2622` | 主要文字 |
| 灰青 | `#68736D` | 次级说明 |
| 竹线 | `#CFC6B5` | 分隔线与禁用边界 |

正文与背景的对比度至少达到 WCAG AA；漆朱和铜金不单独承担状态含义，始终配合文字、图标或形状。

### 3.3 字体与图形

- 正文使用系统中文无衬线字体栈：`PingFang SC`、`Microsoft YaHei`、`Noto Sans CJK SC`、`system-ui`；
- 器物名称、NPC 引语和章节标题可使用系统楷体作为点缀，但不用于小字号正文；
- 器物主视觉采用细节精致但明确非写实、非 3D 的二维插画，本轮使用内联 SVG 绘制漆木首饰盒，不依赖外网图片；
- 插画负责器物整体形态、可检查位置和审美氛围，文字观察卡负责细纹、标记、锁扣结构等需要准确传达的鉴定事实；
- 局部观察采用构图强化的插画裁切、示意轮廓和位置标注，不把插画像素伪装成足以独立下结论的微观证据；
- 使用细密纸纹、漆面高光和铜件质感，透明度保持克制；
- 图标全部使用内联 SVG，并提供可读文本或 `aria-label`。

### 3.4 动效

- 状态切换为 `120—220ms` 的淡入、轻微位移和颜色过渡；
- 新证据使用一次短暂描边和收录反馈，不使用持续闪烁；
- 价格重估使用数字过渡与明确原因文案；
- 不使用视差、长距离滑动或阻塞操作的过场；
- `prefers-reduced-motion: reduce` 时关闭非必要位移和数字动画。

## 4. 响应式框架

### 4.1 桌面宽屏

当视口宽度不小于 `1180px` 时使用三栏：

1. 左侧 `240—280px`：案件档案、公开 NPC 特征、本轮目标；
2. 中央 `420—440px`：完整玩家手机画布；
3. 右侧默认收起的开发复盘栏，展开宽度 `360—420px`。

开发复盘按钮位于手机画布之外，不能混入玩家主导航。老师首次打开只看到整洁玩家体验；需要解释系统时再展开精确状态和公式。

### 4.2 中等宽度

`720—1179px`：

- 保留中央玩家画布；
- 左侧案件档案收进画布顶部的“案件摘要”抽屉；
- 开发复盘作为页面外侧抽屉，默认关闭。

### 4.3 手机

小于 `720px`：

- 玩家画布铺满视口；
- 不显示桌面外框、左侧档案和开发栏；
- 页面最小宽度 `320px`；
- `390 × 844` 为主要验收视口；
- 不产生页面级横向滚动。

## 5. 信息架构

玩家只看到五个阶段：

1. 开店；
2. 来客；
3. 调查；
4. 交易；
5. 复盘。

证据簿是从调查和交易进入的只读信息层，不占用独立阶段。NPC 回应使用同阶段内的反馈页或底部面板，不再让进度条产生额外伪阶段。

### 5.1 全局头部

- 品牌“掌眼”；
- 案件编号；
- 五阶段进度；
- 当前阶段名称；
- 证据簿入口；
- 不显示开发标签和 Mock 文案。

### 5.2 资源呈现

调查行动点和议价容量必须使用不同容器：

- 调查行动点：罗盘/刻度式资源卡，说明“检查、询问、检测使用”；
- 议价容量：谈判筹码/轮次式资源卡，说明“正式报价使用”；
- 调查阶段突出行动点，议价容量仅作次级预告；
- 交易阶段突出议价容量，行动点降为只读回顾；
- 调试阶段显示精确生成公式，玩家界面只显示剩余精确值和用途。

## 6. 页面与任务流

### 6.1 开店

- 首屏展示品牌、案件气质和“开始今日鉴定”主按钮；
- 只保留一个主行动；
- 提供“继续上次演示”仅在本地已有状态时出现，本轮不实现跨刷新存档。

### 6.2 来客

- 展示刘先生头像占位插画、公开性格标签、初始陈述和开价；
- 用一张器物预览卡承载漆木首饰盒；
- 主行动为“接下看看”；
- 次行动为“查看案件摘要”。

### 6.3 调查工作台

同屏只保留三个任务区：

1. 器物主视图与五个可检查热点；
2. 当前线索与温和导向；
3. 询问/对质动作入口。

规则：

- 热点触控目标不小于 `44 × 44px`；
- 已检查热点显示“已记录”，不能通过颜色单独表达；
- 检查结果进入证据发现面板；
- 选择热点后先展示对应的二维局部示意，随后以“看到什么 / 这意味着什么 / 还能核验什么”三层文字呈现鉴定结果；
- 面板只有“收进证据簿并返回调查”一个主按钮；
- 询问时先选具体主题，再可选一条具体证据；
- 不再出现“完整说明 / 只强调部分信息”；
- 不带证据仍可询问，但界面明确提示其推进效率可能较低；
- 语气保留“温和 / 专业 / 强硬”，作为表达修饰项而非动作本体。

### 6.4 证据簿

- 按“器物证据 / NPC 陈述 / 共同检测”分组；
- 每张证据显示名称、客观观察、当前推断、可继续核验方向和可见性；
- “仅自己掌握 / 已向卖家公开”使用文字和图标双重表达；
- 证据簿不提供询问、报价或交易按钮；
- 返回后恢复进入前页面和滚动位置。

### 6.5 NPC 回应

- 清楚区分“卖家原话”“系统可观察变化”“新获得陈述证据”；
- 不直接展示信任、压力等精确内部数值；
- 若价格重估，单独显示旧价、新价和公开原因；
- 主行动为“继续调查”；
- 若已形成可交易依据，提供次行动“进入交易”。

### 6.6 交易

- 首先展示卖家当前报价、系统谨慎参考价和议价容量；
- 自定义报价使用数字输入、减 5/加 5 快捷按钮与提交按钮；
- 每次玩家正式报价消耗 1 点议价容量；
- NPC 反报价是同一轮回应的一部分，不额外消耗玩家容量；
- 第一版议价容量按以下宽松工作公式生成：

```text
基础容量 = 3
信任 >= 55       → +1
成交意愿 >= 65   → +1
压力 >= 75       → -1
控制感 <= 35     → -1
最终容量 = clamp(基础容量 + 修正, 2, 5)
```

当前默认 NPC 初始状态得到 5 点容量。具体参数在开发复盘中标记为“待平衡”。

- 玩家进入交易但尚未正式报价时可以返回调查；
- 提交第一次正式报价后锁定交易阶段，不能再返回调查；
- 议价容量耗尽后仍可接受当前价或拒绝交易；
- 风险转移不作为常驻主按钮，只在人物与案件条件满足时显示在“特殊交易条件”折叠区。

### 6.7 复盘

玩家区不再显示 0—100 客观分。首屏结构：

1. 综合成果等级；
2. 器物客观品质；
3. 实际净收益；
4. 议价表现；
5. 判断质量；
6. 一句结论性反馈；
7. “查看本局因果”与“重新开始”。

等级顺序为：

```text
D < C < B < A < S < SS < SSS
```

物品品质上限采用第一版工作映射：

| 品质 | 综合等级上限 |
|---|---|
| 低价值赝品 | C |
| 重修真品 | A |
| 普通真品 | S |
| 精品 | SS |
| 珍品 | SSS |

内部计算只用于生成等级，不向玩家显示 0—100 分：

```text
等级序号：D=0, C=1, B=2, A=3, S=4, SS=5, SSS=6

原始等级序号 =
round(
  品质序号 × 0.35
  + 净收益表现序号 × 0.30
  + 议价表现序号 × 0.20
  + 判断质量序号 × 0.15
)

综合等级序号 = min(原始等级序号, 品质上限序号)
```

其中：

- 净收益表现必须满足单调性：其他条件相同，净收益提高时等级不得下降；
- 议价表现以进入交易时冻结的开价、当时合法可达最低线和最终成交价计算，避免使用成交后动态形成的临时线；
- 判断质量只读取玩家当时可见证据和行动历史；
- 低价值赝品可以综合封顶 C，但其“判断质量”分项仍可达到 SSS；
- 未成交时，实际净收益为 0，同时单独标记“正确避损”或“错失机会”，不能只靠净收益判断。

开发复盘展开后才显示真实价值、卖家最低线、等级序号、权重、状态变化和每轮公式，并标记“调试信息，不属于玩家界面”。

后续精品、珍品案件可以在结算讲解中增加一张写实器物图，用于文化知识和真品特征讲解；它属于后续正式内容资产，不进入本轮首案验收。

## 7. 交互与可访问性

- 所有按钮、热点、输入和折叠控制具有 `hover`、`focus-visible`、`active`、`disabled` 状态；
- 所有触控目标最小 `44 × 44px`；
- 键盘可以完成开店、调查、收证、询问、报价、结算和复盘；
- 使用原生 `button`、`input`、`details/summary` 或等价可访问组件；
- 焦点不会落入隐藏面板；
- 对话框打开后聚焦标题或首个安全操作，关闭后回到触发按钮；
- 价格、证据和阶段变化通过克制的 `aria-live="polite"` 区域播报；
- 非法报价提供输入附近的文字错误，不只禁用按钮；
- 资源不足时解释“为什么不能继续”并保留可达终局；
- 不使用自动播放声音。

## 8. 技术结构

不直接手工维护第三份内嵌规则。

### 8.1 源文件

新增：

- `hifi/main.tsx`：浏览器入口；
- `hifi/HighFidelityApp.tsx`：玩家任务流与开发复盘壳；
- `hifi/components/`：资源卡、器物视图、证据卡、对话反馈、交易面板、等级结算；
- `hifi/styles.css`：视觉系统与响应式样式；
- `hifi/index.html`：构建壳；
- `vite.hifi.config.ts`：独立高保真构建配置；
- `generate-hifi.mjs`：构建后把 JS/CSS 内联为单文件；
- `tests/hifi-html.test.mjs`：单文件结构和关键契约；
- `tests/hifi-flow.test.mjs`：新等级、双资源与披露行为测试。

复用：

- `content/lacquer-box.ts`：案件内容；
- `game/resolve-action.ts` 与 `game/types.ts`：规则核心；
- React 19 与 Vite 8：现有依赖，不新增生产依赖。

### 8.2 输出

`generate-hifi.mjs` 生成：

- `public/掌眼_高保真教师演示.html`；
- 正常项目构建后由现有 public 复制流程进入 `dist/client/`。

最终 HTML：

- 只有内联样式和内联脚本；
- 不引用 CDN、远程字体、远程图片或外部模块；
- 包含 `lang="zh-CN"`、viewport、描述和主题色；
- 能通过 `file://` 直接打开。

### 8.3 状态与错误

- UI 只通过规则核心的公开接口提交行动并读取结果；
- 不在组件内复制接受线、状态 delta 或后验公式；
- 非法行动返回明确错误状态，UI 不自行扣除资源；
- 页面刷新恢复初始演示状态，本轮不实现持久存档；
- 运行时异常在开发控制台记录，玩家区显示可重新开始的通用错误卡，不暴露堆栈。

### 8.4 最终 H5 载体边界

- 最终产品是通过微信聊天、公众号文章或类似入口中的网址打开的普通响应式网页；
- 当前不制作“微信小游戏”项目，不需要以小游戏 AppID、微信开发者工具代码包和小游戏提审作为发布链路；
- Unity/团结引擎不是当前路线的必经步骤；
- 最终公开版本需要可访问的托管地址与 HTTPS，本轮单文件 HTML 继续用于离线演示；
- 若后续需要微信登录、JS-SDK 分享、支付或其他平台能力，再为对应能力单独确认公众号配置、授权域名和合规要求，不预先把这些能力混入核心游戏。

## 9. 测试与验收

### 9.1 测试先行

实现前新增会失败的测试，至少覆盖：

- 高保真输出文件存在且自包含；
- 页面不含旧 0—100 客观分、70 分胜利线和抽象披露按钮；
- 页面包含调查行动点、议价容量、具体证据选择和 `D—SSS` 结算；
- 正式报价只消耗议价容量，不消耗调查行动点；
- NPC 反报价不额外消耗玩家容量；
- 容量为 0 时仍可接受或拒绝；
- 赝品综合等级不能超过 C；
- 判断质量分项不受赝品综合上限截断；
- 相同条件下净收益增加时，净收益表现和综合等级不下降；
- 同一可见历史仍不能读取隐藏真相。

### 9.2 自动验证

- 高保真专项测试；
- 原有规则、低保真、数值实验台测试；
- TypeScript/ESLint/生产构建；
- 项目记忆结构检查；
- `git diff --check`。

### 9.3 真实浏览器验证

桌面视口：

- `1440 × 1000`；
- 验证三栏、开发栏开关、完整关键路径。

手机视口：

- `390 × 844`；
- 验证无横向溢出、触控目标、滚动、证据返回、报价输入和结算。

键盘：

- 从开店开始，不使用鼠标完成一局；
- 检查焦点可见性、顺序、对话框恢复点。

人机交互审查：

- 页面是否始终有一个明确主行动；
- 同屏信息是否符合渐进式披露；
- 调查点和议价容量是否能凭用途而非颜色区分；
- 价格变化、证据公开和 NPC 回应是否具有紧邻原因反馈；
- 调试内容是否始终位于玩家画布之外。

## 10. Git 与版本边界

低保真与高保真不是“后者覆盖前者”，而是两个用途不同的可运行制品：

- 低保真：保留规则调试、快速定位和历史对照；
- 高保真：承担老师演示和玩家体验审查；
- 数值实验台：承担批量模拟和参数实验。

建议后续 Git 历史分成三个可解释提交：

1. 规则对齐与失败测试；
2. 高保真 UI 与单文件生成；
3. 浏览器验证、文档和证据。

每个提交只记录已经完成的那一层，便于比较低保真到高保真的真实增量，也便于单独回退视觉层而不丢失规则工作。
